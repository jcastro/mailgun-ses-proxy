# 2.1.15 audit and release notes

This release is staged for operator review. Publishing a version tag runs the image/release pipeline; merging the source PRs alone does not deploy to a server.

## Included changes

- [PR 1](https://github.com/jcastro/mailgun-ses-proxy/pull/1): atomic SES event/suppression storage, SNS redelivery deduplication, persistent suppression state and retry retention for known events.
- [PR 2](https://github.com/jcastro/mailgun-ses-proxy/pull/2): accurate read-only deployment settings; safe input/service error classification without exposing internal error messages.
- [PR 3](https://github.com/jcastro/mailgun-ses-proxy/pull/3): API path authentication, signed dashboard sessions, explicit admin provisioning/recovery, bounded concurrent login attempts and existing-password compatibility.
- [PR 4](https://github.com/jcastro/mailgun-ses-proxy/pull/4): refreshed supported dependencies, a single npm dependency graph for CI/Docker, and an actual container startup test.
- [PR 5](https://github.com/jcastro/mailgun-ses-proxy/pull/5): bounded preparation memory, deferred bulk personalization, preserved recipient-weighted rate limits and in-flight draining on producer errors.
- [PR 6](https://github.com/jcastro/mailgun-ses-proxy/pull/6): retryable failed campaigns rather than deletion after three receives; CC/BCC validation at enqueue and worker boundaries.

## Verification

- Local suite: 295 passed; seven database-dependent tests skipped locally.
- CI separately runs five tests against isolated MySQL: event deduplication, suppression persistence/rollback, and collation-equivalent login identity limits. The two legacy opt-in Prisma tests remain outside this suite.
- Production build and TypeScript checks.
- Docker startup, migrations, health, login, authenticated configuration, and rejection of unauthenticated API paths with extension-like segments.
- Synthetic 5,000-recipient campaign with 100 KB HTML: 100 mocked SES calls and 5,000 saved message IDs. With concurrency two and bulk size 50, at most 200 recipients are prepared ahead, rather than the whole campaign. No real emails sent.
- Independent security review found two candidate regressions (collation aliases and existing long passwords); both have dedicated regression coverage.

## Before deployment

1. Back up the database and deployment configuration. Preserve the previous image digest for rollback.
2. Confirm redrive policies, retention and alarms on both send/event queues and their DLQs. Known failures now remain retryable until SQS policy handles them.
3. Review [dashboard setup and legacy recovery](../../app/dashboard/DASHBOARD.md). Keep the exact existing signing secret for valid sessions; production cookies require HTTPS. New installations require explicit admin credentials. Never commit these values.
4. Reject or correct old queued CC/BCC campaigns. Ghost's normal per-recipient newsletter contract is unchanged.
5. Verify SES quotas and configure local rate/concurrency/bulk limits accordingly. Account-wide coordination across workers is not implemented.
6. Test a controlled send, event ingestion, opens/clicks and suppressions after deployment before any large campaign.

## Remaining limitations

- [Durable attempts/outbox and partial persistence](https://github.com/jcastro/mailgun-ses-proxy/issues/7): SES acceptance followed by a database failure can still produce duplicates on replay. Synthetic suppression record/event persistence also needs an atomic boundary. Exactly-once delivery is not claimed.
- [SQS lease renewal and stage timeouts](https://github.com/jcastro/mailgun-ses-proxy/issues/8): a long/stalled operation can outlive visibility. A single worker and sufficient visibility remain operational requirements, not a full distributed-lock guarantee.
- [Upstream Prisma dependency reports](https://github.com/jcastro/mailgun-ses-proxy/issues/9): six transitive production audit reports remain, five high. See [dependency notes](../dependency-security.md); no forced major downgrade or pre-release adoption.
- SNS deduplication applies to newly processed notification IDs. Historical rows stored under SQS IDs can be counted once again if redelivered after upgrading.

No VPS, Ghost, Discourse, IAM, queue setting or production database was changed during this audit.
